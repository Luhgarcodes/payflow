1. Overview

PayFlow is a backend API for a digital wallet and payments platform. Users keep money in an INR wallet, top it up through a payment gateway, send money to other users, pay merchants through payment links and QR codes, schedule recurring payments, and download statements. Merchants accept payments, issue refunds, receive webhooks and get daily settlements. Support and admin staff review KYC, investigate risk flags and run reconciliation.

The project is designed so that building it end to end exercises every area in the learning roadmap. Money raises the bar on correctness: double-entry bookkeeping, transactions, row locking, idempotency, exactly-once webhook handling and reconciliation are requirements here, not extras. Each requirement is tagged with the roadmap areas it practices, and section 11 shows your coverage.

Starting point: this repository is written in strict TypeScript (tsx for development, tsc builds to dist/). It has a users module with bcrypt password hashing in a layered structure (routes, controllers, services) under /api/v1, Sequelize with PostgreSQL, Redis caching with explicit public or per-user scope and versioned invalidation, central error handling, graceful shutdown, and Docker Compose for Redis. The earlier cricket and practice code and its database tables have been removed; the only table this project owns is users.

MVP: the MUST requirements in phases P0 to P4 form the minimum viable product, a complete and portfolio-ready payments backend on their own. Use the "MVP only" filter to focus on them.

Estimated effort: about 40 to 55 focused days for the MVP and 70 to 100 days for everything, at roughly 6 focused hours a day including tests and docs. Each phase header shows its own estimate.

How to use this page: work through the phases in order. Tick a requirement only when all its acceptance criteria pass and it meets the definition of done in section 12. Progress is saved in this browser.

Learning project only. PayFlow uses a mock payment gateway and fake data. Never store real card numbers, bank details, PAN or Aadhaar numbers, and do not process real money with it. Rules below are simplified and only inspired by real regulations; they are not a compliance guide.

4. Domain rules

Money and ledger

  • All amounts are integers in paise (₹1 = 100 paise), stored as BIGINT and sent in JSON as integers with "currency": "INR". Floats are never used for money.
  • PostgreSQL returns BIGINT as a string in Node. Convert it in exactly one place (the money utility) and never with parseFloat.
  • Double-entry: every money movement is one journal (a row in transactions) with two or more ledger entries whose debits equal its credits.
  • Ledger entries are immutable. Mistakes are corrected with a reversing journal, never with UPDATE or DELETE. A database trigger enforces this.
  • A wallet's balance equals the sum of its ledger entries. The wallets.balance_paise column is a cached copy, updated in the same database transaction as the entries, and reconciliation proves they match.
  • Wallet balances can never go negative. This is enforced by a CHECK (balance_paise >= 0) constraint and by checking the balance after locking the row.
  • System ledger accounts: system:gateway_clearing, system:fees, system:cashback, system:settlement_payable and system:suspense.
  • Rounding: fees and cashback round half up to the nearest paisa. When splitting an amount, the remainder goes to the last share so the parts always sum to the total.

Limits and security

  • KYC tiers (simplified, inspired by prepaid wallet rules): none can only view; min (phone verified) has a maximum balance of ₹10,000 and loads up to ₹10,000 a month; full (PAN and identity verified) has a maximum balance of ₹2,00,000 and can send up to ₹1,00,000 a day.
  • Every debit needs the user's transaction PIN (4 to 6 digits, stored hashed). Five wrong attempts lock the PIN for 30 minutes.
  • Transfers above ₹10,000, and the first transfer to a new beneficiary, need a one-time password (OTP) as step-up verification.
  • A new beneficiary can receive at most ₹5,000 in total during their first 24 hours.
  • PAN and bank account numbers are encrypted with AES-256-GCM and only ever returned or logged masked, for example XXXXXX1234.

Payments

  • Every money-moving POST requires an Idempotency-Key header. The same key with the same body returns the original result. The same key with a different body returns 422 IDEMPOTENCY_KEY_REUSED.
  • P2P transfers are free. Merchant payments carry a merchant discount rate (MDR, default 2% = 200 basis points) taken from the merchant's share at payment time and credited to system:fees.
  • Refunds are allowed only on successful merchant payments, within 180 days. Partial refunds are allowed and the refunded total can never exceed the original amount. The MDR is not returned to the merchant.
  • Merchant balances are settled T+1: a daily job moves the previous day's net merchant balance to a mock bank payout.
  • Status flows: top-up created → pending_gateway → succeeded | failed | expired (after 15 minutes); transfer and payment processing → succeeded | failed, and succeeded → reversed by an admin only; refund pending → succeeded | failed.

General

  • All timestamps are stored in UTC. Statements, monthly limits and insights use the Asia/Kolkata calendar month.
  • Every error response has a stable machine-readable code, for example INSUFFICIENT_BALANCE, LIMIT_EXCEEDED, KYC_REQUIRED, PIN_LOCKED or WALLET_FROZEN.
  • Users and merchants are soft-deleted with is_active = false. Financial records are never deleted.
  • Unique fields (email, phone) are unique among active rows only, using partial unique indexes.

9. Non-functional requirements

IDCategoryRequirement
NFR-01CorrectnessZero tolerance: every journal balances, every wallet balance equals its ledger sum, and daily reconciliation reports zero mismatches.
NFR-02CorrectnessExactly-once effect for money movements under client retries, duplicate or out-of-order webhooks, and process crashes. A failed request never leaves a partial journal.
NFR-03ConsistencyConsistency over availability: when PostgreSQL is unavailable, money-moving endpoints fail closed with 503. Balances are never served from a stale cache after a write.
NFR-04Performancep95 under 100 ms for balance reads and under 400 ms for transfers at 100 transfers per second on a single instance, with zero deadlocks.
NFR-05PerformanceA payment notification reaches the connected Socket.IO client in under 500 ms.
NFR-06ScalabilityThe API is stateless: tokens, rate limits, OTPs, locks and sockets work correctly with 3 instances behind a load balancer.
NFR-07SecurityPasswords and PINs hashed with bcrypt (cost 10 or more). PII encrypted at rest and masked in responses and logs. No secrets in the repository. OWASP Top 10 reviewed.
NFR-08Abuse protectionAuth endpoints: 5 requests per minute per IP. Money-moving endpoints: 10 per minute per user. Everything else: 100 per minute per user.
NFR-09AuditabilityEvery money movement is traceable from request ID to transaction, ledger entries and webhook deliveries. Financial and audit records are append-only.
NFR-10ReliabilityGraceful shutdown finishes in-flight requests and the active job within 10 seconds. Jobs survive a worker restart.
NFR-11ObservabilityEvery log line is JSON with a request ID. Business metrics (payments per minute, failure rate, webhook lag) are exported.
NFR-12QualityAt least 90% line coverage on the ledger and money modules, 80% on other services, 70% overall. CI blocks merges when lint or tests fail.
NFR-13MaintainabilityOnly the ledger module writes ledger rows. No business logic in routes or controllers.
NFR-14DocumentationEvery endpoint is described in OpenAPI, including error codes and idempotency behaviour.

12. Definition of done

A requirement counts as done only when all of these are true:

  • All acceptance criteria pass.
  • Request bodies, params and query strings are validated with Zod, and errors use the standard format with a code.
  • Unit tests cover the service logic. An integration test covers the happy path and at least one failure path.
  • Anything that moves money has a test asserting the ledger still balances afterwards.
  • The endpoint is documented in OpenAPI.
  • Any schema change is a migration, not sync().
  • No PII or secrets appear in logs, and new log lines are structured.
  • npm run typecheck passes in strict mode with no any, @ts-ignore or unchecked casts on request data.
  • Lint passes and the code is merged through a pull request with a conventional commit message.
